KPI Anomaly Detection
Agent — Technical Flow

6-layer pipeline: data ingestion → feature engineering → ensemble detection → causal inference → intelligence → communication → AI orchestration. All 5 pipeline layers built and quality-tested. Power BI dashboard pending. Layer 6 orchestration architecture defined.
Execution Summary

What Has Been Built

A 6-layer automated KPI monitoring pipeline processing 731 days (2024-01-01 → 2025-12-31) of synthetic e-commerce data. The pipeline ingests raw transactional tables, engineers 6 temporal features per KPI, runs a 3-method ensemble anomaly detector, traces root causes through a causal graph with statistical inference, quantifies dollar impact, generates priority-ranked recommendations (playbook + Claude AI hybrid), formats and routes alerts by audience and channel, and stores everything in a Power BI-ready star schema. A Claude-based orchestration agent (Layer 6) ties all layers together and runs the pipeline autonomously each morning.

The system monitors 12 tiered KPIs across 731 days (8,772 KPI-day evaluation pairs total). Of those, 75.5% are classified as normal, 22.5% go on the watch list, and 2.1% are confirmed anomalies (181 events across 68 unique dates — 9.3% of all days had at least one confirmed anomaly). Of the 181 anomalies, 8.3% had all three ensemble methods agree simultaneously, indicating the highest-confidence detections.

Data Foundation
Data Foundation — Ingestion, Storage & Feature Engineering
ingest_and_engineer.py → processed_kpi_features.csv (731 × 183) → SQLite: processed_kpis
Step 1.1 — Source Data
What data does the system start with?
The system starts with 8 CSV files covering 731 days of e-commerce activity. The master dataset combines them into one analytical table (731 rows × 33 columns). Ground-truth anomaly labels (anomaly_flag, anomaly_event, anomaly_kpi) are embedded here, used later to validate detection accuracy.
Fact tables: orders · order_items · inventory_daily · marketing_spend_daily · website_traffic_daily · anomaly_log
Dimension tables: customers (10,000 rows — segment, LTV, loyalty status) · products (500 rows — category, price, gross_margin = 0.4968)
Ground truth: 20 labeled anomaly days across 731 — used to validate all detection methods
Step 1.2 — KPI Tiers
Which KPIs are monitored, and how urgently?
The 12 monitored KPIs are split into 3 tiers based on business criticality. Tier determines how quickly an alert fires, which detection methods apply, and how the ensemble votes are capped. Exogenous variables (economic_index, seasonal_index, consumer_sentiment, marketing_pressure) are used as model inputs but are not themselves detection targets.
Tier 1 — Alert immediately: total_revenue_usd · n_orders · avg_roas · conversion_rate

Tier 2 — Alert within 1hr: return_rate · n_stockouts · avg_order_value_usd · bounce_rate

Tier 3 — Daily digest: total_clicks · sessions · inventory_health · avg_discount_pct
Step 1.3 — Feature Engineering
What 6 signals are computed for every KPI, and what does each one mean?
For each of the 25 KPI columns, 6 temporal features are computed — turning a raw daily number into a rich signal the detection models can interpret. The result is 183 columns total (33 raw + 25 KPIs × 6 features). Every feature answers a specific question about how today's value compares to recent history.
Feature Column Suffix Formula Plain-language definition
Rolling Mean _rolling_mean mean(kpi[t-6 : t]) The average value of this KPI over the past 7 days. Acts as a self-updating "what's normal lately" baseline. Used as the reference point for the Z-score below.
Rolling Std Dev _rolling_std std(kpi[t-6 : t]) How much this KPI typically fluctuates from day to day over the past 7 days. A naturally volatile KPI (e.g. total_clicks) will have a larger std, meaning it needs a bigger absolute swing before it looks anomalous.
Z-Score _z_score (kpi[t] − mean) / std How many standard deviations today's value sits above or below the 7-day average. A z-score of +2.5 means today's value is 2.5 standard deviations above normal — a rare event under normal conditions. This is the core statistical detection signal.
Week-over-Week _wow_change (kpi[t] − kpi[t-7]) / |kpi[t-7]| How much this KPI has changed compared to the same day last week (e.g. Monday vs. last Monday). Compares equivalent days, so it's stable against weekly seasonality. Catches gradual week-on-week erosion that the 7-day window might miss.
Month-over-Month _mom_change (kpi[t] − kpi[t-30]) / |kpi[t-30]| How much this KPI has changed compared to 30 days ago. Catches slow structural drift — a KPI declining steadily for weeks will have a large negative MoM even before its 7-day Z-score becomes extreme.
1-Day Lag _lag_1 kpi[t-1] Yesterday's raw KPI value. Feeds the machine learning models (Isolation Forest, LSTM) so they can see the sequential context — the direction the KPI was moving before today.
L2
Detection
Anomaly Detection Engine — 3-Method Ensemble with Voting
5 scripts → method_a/b/c_results.csv → ensemble_voting_matrix.csv (8,772 × 31) → anomaly_results.csv (181 × 25)
Method A — Statistical Baseline
Fast rules-based detection across all 12 KPIs
Three independent sub-flags (A1, A2, A3) fire when a KPI crosses a statistical threshold. Method A is deliberately over-sensitive — it catches every genuine anomaly (100% recall) at the cost of many false alarms. The ensemble in Step 2.3 filters those out.
A1 — Z-score threshold: |z| > 2.5 (Tier 1/2) or 3.0 (Tier 3). In this dataset the max z-score is 2.268, so A1 fires zero times — the 7-day window tracks the series too closely to produce large z-scores.

A2 — STL residual: Decomposes each KPI into trend + seasonality + residual (STL, period=7, robust=True), then applies z-score to the residual only. Separating trend and seasonality makes the residual more sensitive. Primary detection signal: fires 367 times.

A3 — WoW + MoM combined breach: Fires when both WoW > ±20% AND MoM > ±15% simultaneously (Tier 1/2). Catches structural multi-week decline. Fires 1,602 times.

Result: method_a_flag = A1 OR A2 OR A3 → 1,886 total fires (21.5% of all 8,772 KPI-day pairs). Recall = 100% on 20 ground-truth days.
Method B — Isolation Forest
Unsupervised ML catches multi-KPI correlated anomalies
Isolation Forest looks at all 29 raw KPI columns together (not one at a time) and identifies days where the overall pattern of KPI values is unusual. It catches correlated events — e.g. sessions spiking while conversion_rate drops — that a univariate check would miss because neither KPI alone looks extreme enough.
Input: 29 raw KPI columns only — engineered features excluded to avoid data leakage into detection.

Training: StandardScaler + IsolationForest(contamination=0.05, n_estimators=100) fit on rows 0–583 (80% = 2024-01-01 to ~2025-07-31). Scored on all 731 rows for a full historical audit.

Output: One flag per day (not per KPI). 34 of 731 days flagged (4.7%). Score separation is clean: all 34 flagged days have a positive anomaly score; all 697 non-flagged days have a negative score. Each flagged day reports its top-5 KPI contributors by standardised absolute deviation.

Recall: Correctly flags 8 of the 20 ground-truth days. Misses 12.
Method C — Prophet Forecasting
Time-series forecasting for Tier 1 KPIs only
Prophet builds a full probabilistic forecast for each Tier 1 KPI — modelling trend, weekly seasonality, yearly seasonality, and three external factors. An anomaly fires when the actual value falls outside the 95% prediction interval. This is the strongest method for catching holiday-driven and structural events.
Scope: 4 Tier 1 KPIs × 731 days = 2,924 rows. Only Tier 1 KPIs receive this treatment — it's the most compute-intensive method.

Config: interval_width=0.95, weekly_seasonality=True, yearly_seasonality=True. Regressors: economic_index, seasonal_index, marketing_pressure.

Flag rule: actual < yhat_lower OR actual > yhat_upper.

Coverage on non-anomaly days: total_revenue_usd, n_orders, conversion_rate = 100% (no false alarms). avg_roas = 94.5% (its high natural volatility causes a few normal days to fall outside the 95% CI — statistically expected).

Recall: Flags 8 of the 20 ground-truth days. The same 8 as Method B.
Step 2.3 — Ensemble Voting
How the three methods are combined into a final verdict
Each method casts a vote for every KPI-day pair. A confirmation requires at least 2 votes. Severity is assigned based on how many methods agreed and which tier the KPI belongs to. This filtering step removes 96% of Method A's false positives while keeping all high-confidence detections.

L3
Root Cause
Root Cause Analysis — Dependency Graph + Causal Inference + External Driver Check
4 scripts → rca_graph (181×18) → rca_causal (181×40) → rca_results (181×52) → rca_assembly.csv (181×45)
Step 3.1 — Dependency Graph Traversal
Which upstream KPI caused this anomaly to happen?
The system has a pre-built map of how KPIs cause each other (a Directed Acyclic Graph). When a Tier 1 KPI fires, the system walks down that map — from the anomalous KPI toward its children — looking for which child KPI was also moving unusually on that day. The child with the largest z-score is identified as the suspected driver, and the process repeats until it reaches a dead end.
Graph structure (effect → cause direction):
total_revenue_usd → n_orders → sessions → bounce_rate / conversion_rate
total_revenue_usd → avg_order_value_usd → avg_discount_pct
avg_roas → total_clicks

Algorithm: Depth-first search (DFS) from anomalous KPI, following edges where |z_score| ≥ 1.5 on the anomaly date. Picks highest |z| child at each node. Tier 2/3 anomalies skip traversal (they are already the driver) — their upstream Tier 1 impacts are identified via nx.ancestors().

Stop reason breakdown (181 total):
Tier 2/3 no traversal: 93 (51.4%) · No anomalous child found: 73 (40.3%) · Leaf node reached: 15 (8.3%)
Depth distribution (88 Tier 1): depth=0: 62 · depth=1: 22 · depth=2: 4
Step 3.2 — Causal Inference
How confident are we that the driver actually caused the anomaly?
Two statistical methods quantify confidence in the root cause. CausalImpact estimates whether removing the suspected driver would have prevented the anomaly (runs on HIGH severity only). DoWhy estimates the average causal effect of the driver on the outcome KPI and stress-tests the estimate to ensure it's not explained by hidden confounders. Together they produce a root_cause_confidence score from 0 to 1.
CausalImpact: Runs on 14 of 15 HIGH anomalies (1 skipped: pre-period had fewer than 30 rows). 6 of 14 runs found a statistically significant effect. Mean root_cause_confidence for HIGH anomalies: 0.86.

DoWhy: Runs on 26 anomaly records — all HIGH and MEDIUM where the dependency graph found a distinct upstream driver. Covers 7 unique (driver → outcome) pairs. All 26 pass the random common cause refutation test, confirming the causal estimates are robust to unobserved confounding.

root_cause_confidence is available for 35 of 181 anomalies — only those where at least one causal method ran. The remaining 146 use a severity-based fallback in Layer 4 prioritization.
Step 3.3 — External Driver Attribution
Is this something we can actually fix, or is it driven by the market?
Before escalating an anomaly, the system checks whether it was caused by an external market condition beyond the business's control. If so, the actionability score is reduced and, in some cases, the alert is suppressed entirely — preventing the team from being paged about something they cannot influence.
Two external driver types detected:

competitive_pressure (6 events): avg_roas is DOWN and marketing_pressure > 0.30. Competitors are flooding the ad market. Actionability score → 0.45. These 6 are escalation-suppressed.

consumer_sentiment_decline (2 events): return_rate is UP and consumer_sentiment < −0.10. Reduced consumer confidence is driving higher returns. Actionability score → 0.90. Not suppressed — the team can still respond with retention campaigns.

Suppression rules (two hard guards):
HIGH severity anomalies are never suppressed regardless of external cause.
UP direction anomalies are never suppressed — positive surprises are always business-relevant.
All 6 suppressed events are MEDIUM severity + DOWN direction.

Step 4.1 — Business Impact Quantification
What does this anomaly cost the business in dollar terms?
Each anomaly is translated into a concrete financial figure using KPI-specific formulas grounded in real business logic. All baselines are derived from the master dataset averages and the products.csv gross margin. A positive revenue_at_risk means the business is losing money; a negative value means it captured an unexpected gain above forecast.
Key constants: FORWARD_DAYS=7 · AVG_GROSS_MARGIN=0.4968 · ROAS_REVENUE_SHARE=0.30

Example formulas:
total_revenue_usd: (expected − actual) × 7
n_orders: (expected − actual) × AVG_AOV × 7
conversion_rate: (expected − actual) × AVG_DAILY_SESSIONS × AVG_AOV × 7

Derived fields: margin_impact = revenue_at_risk × 0.4968 · monthly_shortfall = revenue_at_risk × (30/7) · impact_pct_of_plan = (risk/7 / avg_daily_rev) × 100

Portfolio totals: Total revenue at risk across all anomalies = $800,375 · Total captured upside = $4,381,894 (upside far exceeds downside — net positive position)

Step 4.3 — Recommendation Engine (Playbook + AI)
What should the team actually do about this anomaly?
Every anomaly gets three recommended actions: what to do in the next hour (IMMEDIATE), what to fix this week (SHORT_TERM), and how to prevent it recurring (PREVENTIVE). These come from a 30-entry deterministic playbook first, then the 101 highest-priority events are enhanced by a Claude AI model that adds context-specific nuance from the root cause narrative, financial impact, and external market conditions.
Playbook: 30-entry dict keyed by (kpi, direction, suspected_driver_kpi) 3-tuples. Falls back to (kpi, direction, None) if no driver-specific entry exists. 100% match rate across 181 anomalies. Each entry specifies owner team and effort level (H/M/L).

AI enhancement (claude-haiku-4-5-20251001): Called for 101 ESCALATE + non-suppressed INVESTIGATE rows (55.8% of anomalies). Prompt caching applied to the ~900-token system prompt (cache_control: ephemeral). MONITOR (74) and SUPPRESSED (6) receive playbook text only — no LLM cost for lower-priority events.

Effort distribution: H=3 (1.7%) · M=60 (33.1%) · L=118 (65.2%)

This ensures Layer 5 always receives a clean, validated input and never operates on partial or corrupt data.

Step 6.1 — Agent Architecture
What is the agent, and what can it do?
The orchestration agent is a Claude Sonnet model that holds the full business rulebook in its system prompt — KPI definitions, alert routing logic, the dependency graph, and the playbook index. It decides which tools to call, in what order, and what to do based on what it detects. No human triage is needed between pipeline layers.
System prompt contains: KPI definitions · business rules · alert routing table · dependency graph structure · playbook index

9 tools available:
fetch_kpis · run_detection · run_rca · score_impact · prioritize · generate_recommendations · send_alert · generate_executive_summary · update_powerbi_dataset

Trigger: 07:00 daily or on new data arrival
Step 6.2 — Daily Decision Flow
What does the agent do, step by step, every morning?
Each morning the agent runs a structured 9-step decision sequence. It fetches today's KPIs, runs all three detection methods, and branches based on what it finds. If anomalies are detected, it runs root cause analysis and impact scoring for each one, prioritises them, generates recommendations, and dispatches alerts — then always ends by writing the daily brief and refreshing the Power BI dataset.
Step 1: fetch_kpis(date=today) — latest row from master_dataset
Step 2: run_detection(methods=['statistical','prophet','isolation_forest'])
Step 3: run_rca(anomaly) — for each HIGH / MEDIUM anomaly
Step 4: score_impact(anomaly, root_cause)
Step 5: prioritize(all_anomalies)
Step 6: generate_recommendations(anomaly, root_cause, impact)
Step 7: send_alert(severity=HIGH) → routes to correct channel
Step 8: generate_executive_summary(all_anomalies, date)
Step 9: update_powerbi_dataset() → Power BI refreshes
Step 6.3 — Technology Stack
What libraries and services power each layer?
The stack is Python-native, using established open-source libraries for each specialised task. The Claude API handles both the orchestration agent and the recommendation enhancement. Alerts are delivered via SMTP and webhook integrations.
